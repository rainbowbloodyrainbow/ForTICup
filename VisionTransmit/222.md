是。**从技术链路看，S3 固件完成后，再补一个电脑端 Python 程序，图传部分就闭环了：**

```text
OV2640
  → ESP32-S3采集JPEG
  → Wi-Fi SoftAP
  → HTTP MJPEG
  → Python/OpenCV接收
  → 实时显示、录像、回放
```

OpenCV 的 `VideoCapture` 可以读取视频源，`VideoWriter` 可以编码保存视频，因此很适合承担电脑端的显示、录像和回放。([OpenCV][1])

但我建议**不要只写一句 `cv2.VideoCapture(stream_url)`**。不同 OpenCV 安装包的视频后端可能表现不同，最稳妥的方案是：

* 首选：`requests` 读取 HTTP MJPEG，手动提取每帧 JPEG，再用 `cv2.imdecode()` 解码；
* 备用：允许用 `cv2.VideoCapture()` 直接打开 URL；
* OpenCV 负责显示、叠加信息、录像和回放。

这样即使 OpenCV 的 FFmpeg/GStreamer 后端没正确支持网络流，程序仍然能工作。

代码写完后，还应完成连续推流、录像文件回放、断线重连以及电机舵机干扰测试。现场使用的电脑或显示器是否满足赛区对显示终端的要求，也需要按正式题面确认。

## MJPEG接收要求

默认不要完全依赖：

```python
cv2.VideoCapture("http://192.168.4.1:81/stream")
```

实现两种接收后端：

### requests后端

作为默认后端。

要求：

1. 使用 `requests.get(..., stream=True)` 连接MJPEG地址。
2. 使用合理的连接和读取超时。
3. 从字节流中寻找JPEG：

   * SOI：`0xFF 0xD8`
   * EOI：`0xFF 0xD9`
4. 使用：

   * `numpy.frombuffer`
   * `cv2.imdecode`
     解码JPEG。
5. 对异常、坏帧和不完整帧做安全处理。
6. 设置最大接收缓冲区限制，避免服务器异常时内存无限增长。
7. 如果长时间没有收到完整帧，应断开并重新连接。
8. 连接失败后自动重连：

   * 第一次等待0.5秒
   * 逐步增加
   * 最大等待5秒
9. 退出程序时能够立即终止网络线程。
10. HTTP连接、响应对象和线程必须正确关闭。

### OpenCV后端

作为可选后端：

```bash
python viewer.py --backend opencv
```

使用 `cv2.VideoCapture` 打开MJPEG URL。

必须检查：

```python
capture.isOpened()
```

连续读取失败后关闭并自动重连。

### 自动模式

支持：

```bash
python viewer.py --backend auto
```

自动模式先尝试 requests 后端；若初始化失败，可以尝试 OpenCV 后端，并输出明确日志。

## 低延迟线程结构

使用独立接收线程。

接收线程只负责：

* 网络读取
* JPEG解码
* 将最新帧和单调时钟时间戳放入队列

显示和录像在主线程完成。

队列容量最多为2或3帧。队列满时丢弃最旧帧，只保留最新图像，避免图传延迟不断累积。

需要统计：

* 接收帧总数
* 解码失败数
* 丢弃帧数
* 重连次数
* 最近接收FPS
* 最近显示FPS
* 最近JPEG大小（如果requests后端可以获得）
* 当前连接状态

共享状态必须使用锁或其他合适的同步方式保护。

使用 `cv2.imshow()`。

```text
H Ball Camera
```

显示画面上叠加：

* 网络连接状态
* 接收FPS
* 显示FPS
* 分辨率
* 丢帧数量
* 重连次数
* 录像状态

* 当前录像文件名

叠加区域应尽量放在画面边缘，不遮挡中央摆杆和钢球。

键盘操作：

* `r`：开始或停止录像
* `s`：保存当前帧截图
* `p`：回放最近一次录像，录像进行中时禁止
* `h`：在终端打印快捷键帮助
* `q` 或 Esc：安全退出

窗口被关闭时也要安全退出。

## 录像要求

使用 OpenCV `cv2.VideoWriter`。

默认格式优先选择稳定、兼容性较好的：

```text
AVI容器 + MJPG编码
```

默认输出目录：

```text
recordings/
```

文件名：

```text
H_BALL_CAM_YYYYMMDD_HHMMSS.avi
```

截图目录：

```text
snapshots/
```

截图文件名：

```text
H_BALL_CAM_YYYYMMDD_HHMMSS_mmm.jpg
```

录像要求：

1. 第一次收到有效帧后才能创建 VideoWriter。
2. 使用实际帧尺寸创建。
3. 必须检查：

```python
writer.isOpened()
```

4. 默认输出FPS为20，可通过参数修改：

```bash
--record-fps 20
```

5. 为了让录像时长尽量符合真实墙钟时间，根据 `time.monotonic()` 对输入帧进行固定帧率重采样：

   * 网络帧过快时适当丢帧
   * 网络帧过慢时可重复最近一帧
   * 录像文件的播放时长应尽量等于实际录像时长
6. 停止录像时必须调用 `release()`。
7. 程序异常退出或收到 Ctrl+C、SIGTERM 时，也必须安全关闭 VideoWriter。
8. 视频流分辨率发生变化时：

   * 停止当前录像
   * 给出明确错误
   * 不要继续向尺寸不匹配的 VideoWriter 写帧
9. 每次结束录像后输出：

   * 文件路径
   * 实际录像时长
   * 写入帧数
   * 文件大小
   * 是否能够重新打开

录像结束后，使用 `cv2.VideoCapture` 对生成文件进行快速验证：

* 文件能否打开
* 是否至少包含一帧
* 帧尺寸是否正确

验证失败时明确警告，但不要删除文件。

## 自测功能

实现：

```bash
python viewer.py --self-test
```

该模式不依赖ESP32硬件。

自测至少包括：

1. 使用OpenCV生成若干张带序号和时间的合成图像。
2. 将图像编码为JPEG。
3. 构造带随机分块的模拟MJPEG字节流。
4. 测试JPEG SOI/EOI解析器能否正确恢复所有图像。
5. 测试坏数据、半帧和缓冲区溢出保护。
6. 创建一个短AVI录像。
7. 重新打开录像并验证：

   * 帧数大于0
   * 分辨率正确
   * 可以正常解码
8. 输出清晰的PASS/FAIL结果。
9. 自测失败时返回非零退出码。

自测不要开启GUI，以便自动执行。

## 健壮性要求

* 使用 `time.monotonic()` 计算FPS、超时和录像时长。
* 不使用系统时间计算时间间隔。
* 捕获并正确处理：

  * requests连接异常
  * HTTP状态码异常
  * JPEG解码失败
  * OpenCV窗口错误
  * VideoWriter打开失败
  * 文件系统权限错误
  * 用户Ctrl+C
* 不允许网络线程异常退出后整个程序无提示地卡住。
* 不允许未限制大小的bytearray持续增长。
* 不允许每帧打印日志。
* 正常运行时每5秒在终端输出一次统计摘要。
* 日志中不要输出Wi-Fi密码。
* 所有路径使用 pathlib.Path。
* 自动创建录像和截图目录。
* 保证所有线程退出后再结束主程序。
* 使用 daemon 线程不能代替正确的停止和 join。
* 网络断开后应一直尝试重连，直到用户主动退出。
* 接收到新连接后应恢复显示和录像。
* 录像过程中断线时，可以重复最后一帧短时间维持时间轴；长时间断线时继续等待，并在画面叠加“DISCONNECTED”。
